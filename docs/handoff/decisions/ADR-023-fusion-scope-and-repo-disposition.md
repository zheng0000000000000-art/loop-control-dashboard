## 1. 배경

`ADR-018`은 "먼저 합치고 상황을 본다"(§3-a)를 택하며 4가지를 **넘기기 전에 사람이 정해야 할 것**으로
미뤄뒀다(`JUDGMENT-LAYER-CONTRACT-v1.md` §4). 2주 관찰(기준선 2026-07-27, 판정 ~2026-08-10)이
끝나기 전에 미리 정할지 판정 시점까지 미룰지는 열려 있었는데, 사용자가 이번에 먼저 답했다.

## 2. 결정 4가지

### 2-1. 상태 원본 — **(a) team-loop을 원본으로**

두 저장소에 갈라져 있던 정의(`RequiredGateCommands`·`SelfTestGateCounts`·영토 목록)의 원본을
team-loop 쪽에 둔다. 이 저장소는 그 정의를 **읽기만** 한다 — 이 저장소가 2026-07-27 하루에만
세 번 고쳤던 "정의 두 벌 → 한쪽만 낡음" 병(`ADR-018` §4 근거)이 이걸로 막힌다.

**따르는 것**: 이 저장소 안에서 지금 하드코딩돼 있는 표(`CodexTerritory.Roots` 등)를 team-loop이
주는 값으로 바꾸는 작업이 남는다. **이건 완화 방향이다** — `FUSION-OBSERVATION-2W.md` 관찰1이
이미 적어둔 대로 "실행자가 자기 영토를 스스로 넓힐 수 없게" 하드코딩한 목적과 충돌할 수 있으므로,
실제 배선 작업은 **별도 지시서로 사람 결재를 받고** 진행한다(이 ADR은 방향만 정한다, 코드는
아직 안 건드림).

### 2-2. 합칠 범위 — **(b) §2 데이터 계약까지**

`JUDGMENT-LAYER-CONTRACT-v1.md` §2의 네 가지(게이트 매니페스트·게이트 보고·처분 기록·컨텍스트 팩)를
team-loop이 실제로 쓰는 스키마로 채택한다. §3 규칙표만(가장 좁음)보다 한 단계 더 나가지만,
**판정 실행기 자체(§4-3)는 옮기지 않는다** — 아래 2-3과 정확히 짝을 이룬다.

**안 하는 것**: 매니페스트를 읽고 명령을 돌려 exit code를 대조하는 러너 코드를 JS로 새로 짓지 않는다.
계약(스키마)만 넘어가고 **실행은 여전히 이 저장소가 한다.**

### 2-3. 판정 실행기 — **재사용(다시 안 쓴다)**

"사용으로"는 기존 판정 실행기(이 저장소의 `server/Harness/`, 23파일 5,417줄)를 **다시 쓰지 않고
그대로 재사용**한다는 뜻으로 받는다. `JUDGMENT-LAYER-CONTRACT-v1.md` §1이 이미 이 조합을 최선으로
지목했다 — *"다시 지어야 하는 것은 테스트로 표현되지 않는 둘(게이트 매니페스트 개념·반증 witness
강제)뿐"*이고 나머지는 team-loop의 기존 `node --test` 러너(테스트 106파일·477케이스)로 표현 가능하다.

**따르는 것**: team-loop이 이 저장소의 하네스를 **외부 명령으로 호출**하는 형태가 유지된다
(`FUSION-OBSERVATION-2W.md` 관찰1이 실측한 것과 같은 경로 — CWD를 대상 저장소에 두고
`dotnet run --project server -- ...`를 돌리는 방식). 이 외부 호출 배선 자체는 아직 없다 —
`tsk_3b9760b2f47c055baecb`(발사기 targetRepo)가 그 준비 조각 하나였을 뿐, team-loop 쪽에서
Local-First 하네스를 정식으로 불러 게이트 보고를 받는 경로는 아직 안 만들어졌다.

### 2-4. 이 저장소의 처분 — **보존(추천, 사용자 위임)**

**추천: 보존.** 아카이브도 폐기도 아니다.

**근거**: 2-3에서 판정 실행기를 다시 쓰지 않고 재사용하기로 했다. 재사용한다는 것은 **이 저장소가
계속 살아서 명령을 받아야 한다**는 뜻이다 — `JUDGMENT-LAYER-CONTRACT-v1.md` §4-4가 이미
"3)에서 다시 안 쓰기로 하면 이 저장소는 계속 살아있어야 한다"고 종속 관계를 적어뒀다.

- **폐기는 배제된다**: 판정 실행기(§4-3)를 재사용하기로 한 순간 폐기와 모순된다 — 재사용할 엔진을
  없앨 수는 없다.
- **아카이브(참조용, 새 작업 안 함)도 안 맞는다**: team-loop이 계속 외부 명령으로 호출하려면
  이 저장소는 **운영 중인 별도 프로세스**여야 한다. 참조만 하는 죽은 저장소로는 §2-3의 재사용이
  성립하지 않는다.
- **다만 이 저장소가 하던 일의 성격은 바뀐다**: 지금까지는 "자기 자신을 재는 게이트"(`ADR-018` §1-2-b)
  였는데, 2-1(상태 원본 team-loop 이관)과 맞물리면 앞으로는 **자기 정의를 스스로 갖지 않고
  team-loop이 주는 정의를 실행만 하는 쪽**으로 역할이 좁아진다. Phase 0/`HS-GATE-P00`의 자기
  검증(이 저장소 자신에 대한 게이트)은 그대로 유지한다 — 그건 이 저장소 자신의 안전장치이지
  team-loop 융합과 별개다.

**이것은 추천이다.** 사용자가 "추천해줘"로 판단을 위임했으므로 이 문서에 결정으로 기록하지만,
다르게 정하고 싶으면 언제든 이 ADR을 폐기하고 사유를 적으면 된다(§6 되돌림 조건과 동일 절차).

## 3. 안 바뀌는 것

- `FUSION-OBSERVATION-2W.md`의 기준선·2주 관찰 일정은 그대로다. 이 ADR은 **§4의 질문에 답한 것**이지
  관찰 결과를 앞당겨 판정한 것이 아니다.
- Phase 0/`HS-GATE-P00` 제약은 그대로다. 이 ADR에 따른 실제 배선(2-1의 하드코딩 제거, 2-3의 외부
  호출 경로 신설)은 **각각 별도 지시서로 진행**하며, 이 ADR 자체는 코드를 바꾸지 않는다.

## 4. 사람이 볼 것

- 2-4(저장소 처분)는 추천이다 — 동의하지 않으면 알려달라, 바로 정정한다.
- 2-1·2-3이 만드는 실제 코드 작업(하드코딩 제거, 외부 호출 배선)은 아직 시작 안 됐다 — 다음
  지시서 대상이다.

## 5. 되돌림 조건

이 ADR의 어느 결정이든 실사용(2주 관찰 또는 그 이후)에서 실측으로 안 맞는 것이 확인되면
이 ADR을 `폐기`로 바꾸고 사유를 적는다. 코드 변경은 아직 없으므로 되돌릴 것이 없다.
