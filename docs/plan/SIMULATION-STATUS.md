# 시뮬레이션 현황 — 미지의 경매장

기계가 잰 수치와 사람이 준 목표를 한 장에 모은다.
**이 문서는 손으로 쓴 것이다.** 수치는 아래 "잰 방법"으로 재현되어야 한다 — 안 맞으면 이 문서가 틀린 것이다.

마지막 갱신: 2026-07-29 · 갱신 주체: 조율자 세션

## 1. 사람이 준 목표

| 항목 | 값 |
| --- | --- |
| 시작 자본 | 20,000 |
| 12회차 자본 | 100,000 이상 |
| 최종 경매 적 자본 | 120,000 ~ 150,000 |
| 상회 업그레이드 품목 | 미정 (1차 제안: 아래 §5) |

**이 수치는 합격선이 아니라 조준점이다.** 사용자 명시: *"내가 주는건 목표에 가깝다로 봐줘."*
그러므로 **진행 판정은 §4의 방향 다섯 부호로 한다.** 수치가 바뀌어도 부호는 안 흔들린다.

## 2. 실측 (2026-07-29, 5시드 x 400회, 세 세션이 독립으로 같은 값 확인)

| 정책 | 중앙값 | 달성률 | RoiMean | TxRoi | 성장률/일 | 승률 | 정보지출 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| blind | 24,131 | 5.50% | 99.5% | 13.9% | 3.78% | 25.7% | 0.0% |
| appraisal | 11,407 | 3.30% | 30.6% | 16.9% | -3.67% | 24.3% | 74.3% |
| demand | 32,964 | 7.25% | 131.4% | 21.2% | 5.26% | 24.8% | 3.9% |
| informed | 13,357 | 4.60% | 55.8% | 24.3% | -1.75% | 23.7% | 77.6% |

**정보 우위 = -43.7%p.** 정보를 사는 정책이 안 사는 정책보다 **나쁘다.**
필요 성장률 14.35%/일 대 실측 5.26%/일 — **2.73~3.05배 모자란다.**

### 잰 방법 (재현용)

```
simulateAuctionEconomy(spec.baseline, { seed, runs: 400, policies, goalThreshold })
provider auction-economy-v1 · seeds 5개 · 지표 EndAssetsP50 / RoiMean / TransactionRoiMean
                                              / DailyGrowthRate / LotWinRate / InformationSpendRate
```

**함정:** `spec` 전체를 넘기면 `InformationSpendRate`가 전 정책 0.00으로 나온다.
`spec.baseline`을 넘겨야 한다. 0.00이 보이면 엔진이 아니라 호출이 틀린 것이다.

## 3. 진단 — 왜 이렇게 나오는가

수치를 만지기 전에 **구조가 셋 빠져 있다.** 이건 밸런스 문제가 아니라 없는 것이다.

### 진단 1. 정보가 판단에 안 쓰인다 (판단 부재)

```js
const shouldBuy = ... (policy.acquisition === 'SELECTIVE' && lot.informationPriority >= policy.minimumPriority)
const playerMax  = information.expectedSale * (1 - targetMarginRate);   // 정보 유무와 무관하게 같은 식
```

살지 말지는 **등급만** 본다. 얼마를 쓸지는 **정보가 있든 없든 같은 식**이다.
그래서 정보값은 지출로만 나가고 행동을 바꾸지 않는다. **가격을 낮춰도 안 고쳐진다** — 회수 실패가 아니라 판단 부재다.

### 진단 2. 물건에 품질이 없다

```js
trueSalePrice = baseValue * demandMultiplier;   // 등급의 baseValue x 수요. 품질 항이 없다
```

같은 등급·같은 계열이면 **두 물건이 기계적으로 동일하다.** 감정할 이유가 원리적으로 없다.
AI가 이름과 설명을 아무리 다르게 생성해도 **밸런스에는 아무 영향이 없다** — 생성이 순수한 껍데기다.

### 진단 3. 봇에 자본이 없다

```js
budget = playerCash * randomBetween(0.6, 1.2);   // 플레이어에 붙은 상대값
```

적이 **플레이어를 따라 커진다.** 최종 경매 적 자본 12~15만이라는 목표를 **표현할 수단이 없다.**
성장해도 상대적 위치가 그대로라 후반이 전반보다 나아지지 않는다.

## 4. 방향 다섯 부호 — 진행 판정 기준

**시뮬레이션 태스크는 전부 이 다섯을 부호로 보고한다.** 값 목표는 최종 조준용으로만 쓴다.

| # | 부호 | 지금 | 원하는 것 |
| --- | --- | --- | --- |
| 1 | 정보가 이득인가 | **-43.7%p** | 양수 |
| 2 | 정보가 행동을 바꾸는가 | **아니오** (같은 식) | 예 |
| 3 | 지배 전략이 없는가 | **아니오** (demand 지배) | 예 |
| 4 | 후반이 전반보다 나은가 | **아니오** (봇이 따라 큼) | 예 |
| 5 | 빌드가 갈리는가 | **아니오** (축이 하나) | 예 |

**왜 부호인가:** 목표 수치는 바뀔 수 있다(사용자가 "수치가 문제일순 있으니"라고 명시).
수치로 판정하면 목표를 조정할 때마다 과거 판정이 전부 무효가 된다. 부호는 그래도 남는다.

## 5. 사슬 — 9단계

```
bl-sim-quality               p30  품질 도입 - 가치를 등급에서 뗀다        [진단 2]
  |- bl-sim-tags             p26  태그 + 감정 1회 = 태그 1개              [진단 1]
  |    |- bl-sim-generation-invariance p26  생성이 밸런스를 안 흔드는지 잰다
  |    |- bl-sim-sets        p26  세트 계약  (+ 시세 의존)
  |    |- bl-sim-commissions p22  의뢰
  |          |- bl-sim-shop-axes    p22  상회 3축                        [부호 5]
  |                |- bl-sim-day-deadline p22  일차 마감 = 게임 오버
  |- bl-sim-series-index     p26  시세를 계열별-일자별 지수로

bl-sim-bot-capital           p30  봇 지속 자본 + 자본 기반 상한 + 성장 곡선  [진단 3, 독립]
```

**순서의 이유:** 품질이 없으면 태그가 붙을 곳이 없고, 태그가 없으면 세트·의뢰가 참조할 것이 없다.
상회 3축은 세트·의뢰가 있어야 축이 갈린다. 일차 마감은 축이 있어야 뒤처짐을 잴 수 있다.

### 상회 업그레이드 1차 제안 (품목 미정 자리)

사용자 의도: *"성장 겸 실패 확인이 되는 구조"* · *"특정 기간동안 무조건 올리게"* · *"뒤쳐지면 게임 오버"*

| 축 | 올리면 | 부호 |
| --- | --- | --- |
| 정보 | 감정 슬롯 / 태그 해금 속도 | 1, 2 |
| 세트 | 보관 칸 / 세트 정산 배수 | 5 |
| 의뢰 | 동시 수주 수 / 납기 여유 | 5 |

**셋 다 필요하다.** 하나면 축이 안 갈려 부호 5가 안 선다.

## 6. 안 정해진 것 (추측으로 채우지 않는다)

- 상회 업그레이드 **품목의 구체 수치** — 축만 제안했다. 값은 `bl-sim-shop-axes`가 정한다.
- 일차 마감의 **뒤처짐 기준선** — `bl-sim-day-deadline`.
- 유찰 손실 — **현재 구조에 없다.** 있다고 가정하고 설계하지 마라(이 오류를 한 번 냈다).
